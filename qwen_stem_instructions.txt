────────────────────────────────────────────────────────────────────────────────
1. OBJETIVO GENERAL
────────────────────────────────────────────────────────────────────────────────

Limbus Split Pro - Local Web Edition será una aplicación web que se ejecuta
íntegramente en el PC local del usuario (servidor en localhost, cliente en el
navegador) para separar una mezcla musical en pistas independientes mediante
modelos locales de inteligencia artificial.

Está dirigida a uso propio e interno. No es un producto comercial, no se
distribuirá a terceros y no requiere firma de código, instalador MSI ni
certificados. Sin embargo, debe mantener estándares profesionales de calidad,
estabilidad y organización del código.

El flujo principal será: cargar una canción, elegir qué separar, procesar,
escuchar las pistas en un mezclador multipista y exportar.

Prioridades, en este orden:
  1. Calidad real de separación.
  2. Sincronización exacta de reproducción y exportación.
  3. Estabilidad y ausencia de archivos silenciosos falsos.
  4. Facilidad de uso.
  5. Privacidad y procesamiento 100% local.
  6. Pipeline de separación maximizado (múltiples etapas en cascada).
  7. Diseño limpio, funcional y agradable.
  8. Licencias y atribuciones correctas.
  9. Reproducibilidad del entorno.

No construyas una aplicación de escritorio nativa, una PWA ni una aplicación
Electron. Construye una aplicación web con servidor Python local y frontend
React que se comunica exclusivamente mediante localhost.

2. STACK TECNOLÓGICO
────────────────────────────────────────────────────────────────────────────────

Backend:
  - Python 3.11+ (versión exacta fijada y documentada).
  - FastAPI como framework web asíncrono.
  - Uvicorn como servidor ASGI.
  - PyTorch como runtime de inferencia.
  - Demucs v4 (htdemucs_ft) como motor principal de separación 4-stem.
  - BSRNN (music_source_separation de ByteDance) para sub-stems de batería.
  - Modelos de de-reverb vocal (investigar y documentar opciones).
  - Modelos experimentales para lead/backing vocals (investigar y documentar).
  - FFmpeg (binario local, no dependiente del PATH del sistema) para
    decodificación de MP3, FLAC, AAC, M4A.
  - soundfile / librosa para lectura/escritura de audio.
  - numpy para operaciones de mezcla y complemento (Other).

Frontend:
  - React 18+ con TypeScript.
  - Vite como bundler y dev server.
  - Web Audio API para reproducción multipista sample-accurate.
  - TailwindCSS o CSS Modules para estilos.
  - Componentes accesibles (ARIA, navegación por teclado).

Comunicación:
  - REST API para operaciones síncronas (metadatos, configuración).
  - Server-Sent Events (SSE) o WebSockets para progreso en tiempo real.
  - Descarga de archivos mediante endpoints REST con Content-Disposition.

Despliegue:
  - Script de arranque (PowerShell y bash) que inicia el servidor local.
  - Opcional: Docker Compose para aislamiento del entorno.
  - El servidor escucha únicamente en 127.0.0.1 (nunca en 0.0.0.0).

5. FLUJO PRINCIPAL
────────────────────────────────────────────────────────────────────────────────

El usuario debe poder:
  1. Arrastrar una canción al navegador o seleccionarla con un input de archivo.
  2. Ver nombre, formato, duración, frecuencia de muestreo y canales.
  3. Elegir exactamente qué elementos desea separar (ver sección 6).
  4. Elegir una carpeta de exportación (mediante la API File System Access
     o, como fallback, descargar un ZIP).
  5. Iniciar la separación.
  6. Ver progreso real y etapa actual del pipeline.
  7. Cancelar de forma segura.
  8. Escuchar simultáneamente todas las pistas generadas en un mezclador web.
  9. Aplicar mute, solo y volumen independiente a cada pista.
  10. Cambiar el punto de reproducción mediante una línea temporal.
  11. Exportar pistas individuales (descarga directa).
  12. Exportar una mezcla con los volúmenes, mute y solo actuales.
  13. Abrir la carpeta de resultados (si File System Access API está disponible)
      o descargar todo como ZIP.

Nunca guardes resultados en una ubicación desconocida. El usuario debe poder
elegir explícitamente dónde exportar o descargar los archivos.

Admite archivos con nombres Unicode, espacios y caracteres especiales.
Nunca construyas rutas concatenando texto sin sanitizar.

────────────────────────────────────────────────────────────────────────────────
6. SELECTOR DE PISTAS
────────────────────────────────────────────────────────────────────────────────

La interfaz debe disponer de controles "Todas" y "Ninguna", además de
selectores individuales organizados por categorías.

Categorías deseadas:

  VOCES:
    • Voces (pista completa de voz).
    • Voz principal (lead vocals).
    • Coros y segundas voces (backing vocals) → MUTEADO POR DEFECTO.
    • Efectos vocales / reverberación vocal → MUTEADO POR DEFECTO.
    • Ruido o artefactos vocales.

  BATERÍA:
    • Batería completa.
    • Bombo (kick).
    • Caja (snare).
    • Toms.
    • Platos (cymbals/hi-hat).

  BAJO:
    • Bajo.

  GUITARRA:
    • Guitarra (pista general).
    • Guitarra acústica → solo si existe un modelo realmente capaz.
    • Guitarra eléctrica → solo si existe un modelo realmente capaz.

  TECLADOS:
    • Piano y teclados (pista general).
    • Piano → MUTEADO POR DEFECTO si se separa de sintes.
    • Sintetizadores → MUTEADO POR DEFECTO si se separa de piano.

  OTROS:
    • Otros instrumentos que puedan separarse mediante modelos reales.
    • Other (complemento matemático de todo lo no seleccionado).

Reglas obligatorias:
  - No muestres opciones falsas ni generes archivos silenciosos para aparentar
    que una separación existe.
  - Si no existe un modelo técnicamente válido:
      • Deja la opción desactivada (disabled) con un tooltip explicativo.
      • Explica por qué no está disponible.
      • No generes una pista vacía.
      • Registra la limitación en el informe.
  - Las pistas marcadas como "MUTEADO POR DEFECTO" deben aparecer en el
    mezclador con mute activado, pero el audio debe existir realmente.
    El usuario puede desmutearlas manualmente.

────────────────────────────────────────────────────────────────────────────────
7. LÓGICA DE OTHER
────────────────────────────────────────────────────────────────────────────────

La lógica de complemento es obligatoria.

  - Si el usuario selecciona solamente "Voces", exporta "Voces.wav" y
    "Other.wav". Other debe contener todo lo que no sea voz.
  - Si selecciona solamente "Batería", exporta "Batería completa.wav",
    sus sub-stems cuando corresponda, y "Other.wav". Other debe contener
    todo lo que no sea batería.
  - Si selecciona varios instrumentos, Other debe contener todo aquello
    que no haya sido seleccionado.
  - Si selecciona todas las categorías, genera Other solamente si queda
    material residual real.
  - Other no debe ser un archivo silencioso creado artificialmente.
  - La suma de las pistas principales y Other debe reconstruir la mezcla
    con el menor error posible.
  - Evita duplicar material cuando se exporta simultáneamente una pista
    general y sus subpistas (ej: si exporta "Batería completa" y también
    "Bombo", "Caja", etc., Other no debe contener la batería duplicada).

Para voces detalladas:
  - Voz principal y coros deben proceder de una separación real.
  - Los efectos vocales (reverb) deben proceder de un modelo de de-reverb real.
  - El ruido debe ser una pista independiente real.
  - Ejecuta internamente las etapas necesarias aunque el usuario no haya
    seleccionado sus resultados intermedios.
  - No obligues al usuario a entender dependencias entre modelos.

Implementación técnica de Other:
  - Other = mezcla_original - suma(pistas_seleccionadas).
  - Realiza la resta en el dominio del sample con precisión float32/float64.
  - Alinea todas las pistas al mismo offset temporal antes de restar.
  - Verifica que Other no sea silencioso (RMS > umbral) antes de exportarlo.
  - Si Other es silencioso, no lo exportes y notifica al usuario.

────────────────────────────────────────────────────────────────────────────────
8. PIPELINE DE SEPARACIÓN EN CASCADA
────────────────────────────────────────────────────────────────────────────────

Este es el corazón de la aplicación. El pipeline maximiza la separación
ejecutando múltiples modelos en secuencia, cada uno refinando el resultado
del anterior.

Arquitectura del pipeline:

  ENTRADA: mezcla.wav (archivo original del usuario)
    │
    ▼
  ┌─────────────────────────────────────────────┐
  │ ETAPA 1: Separación 4-stem (Demucs)       │
  │ Modelo: htdemucs_ft                        │
  │ Salida: vocals, drums, bass, other         │
  └──────────────────┬──────────────────────────┘
                     │
        ┌────────────┼────────────┬──────────────┐
        ▼            ▼            ▼              ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐
  │ ETAPA 2  │ │ ETAPA 5  │ │ (bass    │ │ ETAPA 4      │
  │ Vocals   │ │ Drums    │ │  directo)│ │ Other →      │
  │ cascade  │ │ sub-stems│ │          │ │ instrumentos │
  └────┬─────┘ └────┬─────┘ └──────────┘ └──────┬───────┘
       │            │                           │
       ▼            ▼                           ▼
  ┌──────────┐ ┌──────────┐             ┌──────────────┐
  │ ETAPA 2a │ │ kick     │             │ piano        │
  │ De-reverb│ │ snare    │             │ synths       │
  │ vocals   │ │ toms     │             │ guitar       │
  └────┬─────┘ │ cymbals  │             │ (experimental│
       │       └──────────┘             └──────────────┘
       ▼
  ┌──────────┐
  │ ETAPA 3  │
  │ Lead vs  │
  │ Backing  │
  │ vocals   │
  │(experim.)│
  └──────────┘

Definición detallada de cada etapa:

ETAPA 1 — Separación 4-stem:
  Modelo: Demucs htdemucs_ft (Meta FAIR).
  Entrada: mezcla original.
  Salida: vocals.wav, drums.wav, bass.wav, other.wav.
  Estado: Probado, calidad profesional.
  Licencia: Código MIT, pesos CC BY-NC 4.0 (viable para uso propio).
  Notas: Esta etapa se ejecuta siempre, independientemente de lo que
  el usuario seleccione, porque las etapas posteriores dependen de ella.

ETAPA 2 — De-reverb vocal:
  Modelo: Investigar entre opciones disponibles:
    - Modelos de UVR (Reverb-Echo, DeReverb).
    - Modelos académicos de speech dereverberation adaptados a música.
  Entrada: vocals.wav (salida de Etapa 1).
  Salida: vocals_dry.wav (voz sin reverb), vocals_reverb.wav (solo reverb).
  Estado: Funcional pero calidad variable. Documentar honestamente.
  Comportamiento: vocals_reverb.wav se presenta MUTEADO POR DEFECTO.
  Si no se encuentra un modelo adecuado:
    - Desactivar la opción de separar reverb vocal.
    - vocals_dry.wav = vocals.wav (sin procesar).
    - Documentar la limitación.

ETAPA 3 — Lead vs Backing vocals:
  Modelo: Investigar opciones:
    - Modelos de UVR para separación lead/backing.
    - Modelos académicos (verificar disponibilidad de pesos).
  Entrada: vocals_dry.wav (o vocals.wav si Etapa 2 no está disponible).
  Salida: lead_vocals.wav, backing_vocals.wav.
  Estado: EXPERIMENTAL. No hay modelos públicos con calidad profesional
  verificada en 2026.
  Comportamiento:
    - backing_vocals.wav se presenta MUTEADO POR DEFECTO.
    - Si el modelo no existe o la calidad es inaceptable:
        • Desactivar las opciones "Voz principal" y "Coros" en la UI.
        • Explicar: "No existe un modelo público fiable para esta
          separación en la actualidad."
        • No generar archivos silenciosos.
    - Si se encuentra un modelo funcional pero de calidad media:
        • Marcar claramente como "Experimental - calidad variable".
        • Permitir al usuario activarlo bajo su responsabilidad.

ETAPA 4 — Separación de instrumentos en "Other":
  Modelo: Investigar opciones:
    - Modelos multi-instrument (MusDB18-trained, etc.).
    - BSRNN con targets específicos.
  Entrada: other.wav (salida de Etapa 1).
  Salida: guitar.wav, piano.wav, synths.wav, etc.
  Estado: EXPERIMENTAL / PARCIAL.
  Comportamiento:
    - Piano y sintes se presentan MUTEADOS POR DEFECTO si se separan.
    - Si no hay modelo fiable para una categoría:
        • Desactivar la opción en la UI.
        • No generar archivos silenciosos.
    - Guitarra acústica vs eléctrica: desactivada salvo que exista
      un modelo verificado.
    - Si la separación es de baja calidad, marcar como "Experimental".

ETAPA 5 — Sub-stems de batería:
  Modelo: BSRNN de ByteDance (music_source_separation) con checkpoints
  de drums sub-stems.
  Entrada: drums.wav (salida de Etapa 1).
  Salida: kick.wav, snare.wav, toms.wav, cymbals.wav.
  Estado: Probado, calidad profesional.
  Licencia: MIT (código y pesos, verificar cada checkpoint).
  Notas: Esta es la separación de sub-stems más fiable disponible.

Reglas del pipeline:
  1. Las etapas se ejecutan solo si el usuario ha seleccionado algo que
     las requiere. No proceses Etapa 5 si el usuario solo quiere voces.
  2. Sin embargo, si el usuario selecciona "Voz principal" (Etapa 3),
     debes ejecutar Etapa 1 y Etapa 2 internamente aunque no haya
     seleccionado "Voces" o "Reverb vocal" explícitamente.
  3. El progreso debe mostrar la etapa actual: "Etapa 1/5: Separando
     mezcla en 4 stems...", "Etapa 2/5: Eliminando reverb vocal...", etc.
  4. Si una etapa falla, registra el error, continúa con las etapas
     independientes y marca las pistas afectadas como no disponibles.
  5. Nunca generes una pista vacía para rellenar un hueco del pipeline.
  6. Cada etapa debe verificar que su entrada no es un archivo silencioso
     antes de procesar (RMS > umbral configurable).

Gestión de dependencias entre etapas:
  - El usuario no necesita saber qué etapas se ejecutan internamente.
  - Si selecciona "Bombo", el sistema ejecuta Etapa 1 + Etapa 5.
  - Si selecciona "Voz principal", el sistema ejecuta Etapa 1 + Etapa 2
    (opcional) + Etapa 3.
  - Si selecciona "Piano", el sistema ejecuta Etapa 1 + Etapa 4.
  - La UI muestra un resumen: "Se ejecutarán 3 etapas de separación"
    antes de iniciar.

9. INVESTIGACIÓN Y MOTOR DE SEPARACIÓN
────────────────────────────────────────────────────────────────────────────────

Investiga modelos actuales antes de escogerlos. Utiliza fuentes primarias:
repositorios oficiales, model cards, publicaciones de los autores y licencias
incluidas con los pesos.

Condiciones obligatorias:
  - Procesamiento completamente local.
  - Sin subir canciones a ningún servidor externo.
  - Sin llamadas a APIs externas durante la separación.
  - Sin descargar modelos silenciosamente mientras se procesa una pista.
  - Gestión explícita de la descarga e instalación de modelos.
  - Hash SHA-256 de cada modelo descargado.
  - Registro de procedencia, versión, licencia, autor y capacidades.
  - Diferenciación entre licencia del código y licencia de los pesos.
  - Prohibición de asumir que los pesos son comerciales porque el
    repositorio sea MIT.

Dado que es uso propio e interno:
  - Se permite el uso de modelos con licencia CC BY-NC (como Demucs).
  - Se permite el uso de modelos con licencias ambiguas si se documenta
    claramente la ambigüedad y el riesgo.
  - No se requiere autorización comercial explícita.
  - Aun así, prefiere modelos con licencias claras (MIT, Apache 2.0)
    cuando existan alternativas de calidad equivalente.

Implementa un manifiesto (MODEL_MANIFEST.json) con:
  - Identificador único.
  - Ruta relativa dentro de models/.
  - Hash SHA-256.
  - Tamaño esperado.
  - Versión.
  - Origen (URL del repositorio o release).
  - Licencia del código.
  - Licencia de los pesos.
  - Evidencia de licencia (enlace al archivo LICENSE o model card).
  - Autor y atribución requerida.
  - Capacidades (qué stems puede separar).
  - Estado: "production", "experimental", "unavailable".
  - Notas sobre calidad y limitaciones conocidas.

Implementa un verificador de modelos:
  - Al arrancar el servidor, verifica que todos los modelos requeridos
    están presentes y que sus hashes coinciden.
  - Si falta un modelo, muestra instrucciones claras de descarga.
  - Si un hash no coincide, alerta y no utilices ese modelo.
  - Los modelos marcados como "experimental" pueden omitirse sin error.
  - Los modelos marcados como "unavailable" desactivan su opción en la UI.

────────────────────────────────────────────────────────────────────────────────
10. ARQUITECTURA DEL MOTOR
────────────────────────────────────────────────────────────────────────────────

La aplicación tiene dos componentes principales que se ejecutan en el mismo
PC pero como procesos separados:

Componente 1 — Servidor FastAPI (Python):
  - Escucha en 127.0.0.1:8000 (nunca en 0.0.0.0).
  - Gestiona la API REST, SSE/WebSockets y la descarga de archivos.
  - Orquesta el pipeline de separación.
  - Ejecuta los modelos de IA.
  - Gestiona el sistema de archivos local (lectura de entrada, escritura
    de salida).

Componente 2 — Frontend React (navegador):
  - Se sirve desde el propio FastAPI (archivos estáticos) o desde Vite
    dev server en desarrollo (con proxy a FastAPI).
  - Gestiona la UI, el mezclador y la interacción del usuario.
  - Se comunica con el backend exclusivamente mediante HTTP/WebSocket
    a localhost.

Comunicación:
  - REST para: subir archivo, obtener metadatos, iniciar separación,
    descargar pistas, exportar mezcla, obtener estado de modelos.
  - SSE para: progreso de separación en tiempo real (etapa, porcentaje,
    ETA, errores).
  - WebSocket (alternativa a SSE): si se necesita comunicación bidireccional
    (ej: cancelar proceso).

Cancelación:
  - El frontend envía una señal de cancelación (REST o WebSocket).
  - El backend detiene la etapa actual de forma limpia.
  - Se eliminan los archivos temporales de la etapa cancelada.
  - Se conservan los resultados de etapas ya completadas.
  - Se notifica al frontend del estado final.

Limpieza:
  - Al cerrar el servidor (Ctrl+C o señal), finaliza cualquier proceso
    de inferencia en curso.
  - No deja procesos Python huérfanos.
  - Limpia archivos temporales de sesiones anteriores al arrancar.

15. REPRODUCCIÓN DE AUDIO EN EL NAVEGADOR
────────────────────────────────────────────────────────────────────────────────

La reproducción debe comportarse como un mezclador multipista preciso.

Utiliza la Web Audio API con las siguientes reglas estrictas:

  - Un único AudioContext maestro para toda la aplicación.
  - Todas las pistas se cargan como AudioBuffer mediante fetch +
    audioContext.decodeAudioData().
  - Cada pista tiene su propio AudioBufferSourceNode (o se reutilizan
    tras cada stop/seek).
  - Cada pista tiene su propio GainNode para volumen/mute.
  - Todos los GainNode se conectan al destination del AudioContext.

Sincronización:
  - Todas las pistas deben comenzar en el mismo sample.
  - Utiliza audioContext.currentTime como reloj maestro.
  - Al dar play, programa todos los sourceNode.start() con el mismo
    offset calculado desde currentTime.
  - Al hacer seek, detén todos los sourceNode, calcula el nuevo offset
    y vuelve a crearlos y programarlos.
  - No utilices setTimeout ni setInterval para la sincronización; usa
    requestAnimationFrame solo para actualizar la UI (barra de progreso).

Solo logic:
  - Cuando al menos un solo está activo, solo suenan las pistas en solo
    (excepto las que también estén en mute).
  - Implementa esto ajustando el gain de cada GainNode:
      • Si hay solos activos y esta pista no tiene solo → gain = 0.
      • Si esta pista tiene mute → gain = 0.
      • En otro caso → gain = volumen del slider.
  - Los cambios de gain deben usar linearRampToValueAtTime con una
    rampa corta (5-20ms) para evitar clics.

Mute/Solo/Volumen:
  - Mute no detiene la reproducción.
  - Solo no detiene la reproducción.
  - Cambiar volumen no detiene la reproducción.
  - Estos cambios no devuelven el cursor al inicio.
  - Utiliza rampas de ganancia cortas (5-20ms) para evitar clics.

Seek:
  - Seek no produce rebote, doble ataque, clic o silencio perceptible.
  - Implementa crossfade o rampas de ganancia cortas al hacer seek.
  - Tras seek, continúa desde el punto seleccionado.

Atajo de espacio:
  - Espacio alterna play/pausa.
  - No se activa al escribir en campos de texto, textareas o selects.
  - No se activa mientras un diálogo modal está abierto.
  - Previene el scroll por defecto del navegador al pulsar espacio.

Gestión de AudioContext:
  - El AudioContext puede estar en estado "suspended" hasta la primera
    interacción del usuario. Resume() al primer clic.
  - Gestiona el cambio de dispositivo de audio del sistema (el navegador
    lo maneja automáticamente en la mayoría de casos).
  - Si el AudioContext se cierra o falla, muestra un error claro y
    permite reiniciarlo.

18. EXPORTACIÓN DE MEZCLA
────────────────────────────────────────────────────────────────────────────────

Añade un botón "Exportar mezcla".

La mezcla exportada debe respetar exactamente:
  - Volumen por pista (aplicado como ganancia lineal).
  - Mute (pistas muteadas no contribuyen).
  - Solo (si hay solos activos, solo las pistas en solo contribuyen).
  - Alineación sample-accurate.
  - Duración completa.
  - Frecuencia de muestreo de la pista de mayor calidad (o la original).
  - Canales (estéreo si la original es estéreo).
  - Punto inicial común.

Implementación:
  - Realiza la exportación offline en el servidor (Python), no en el
    navegador.
  - El frontend envía al backend el estado actual del mezclador:
    [{track_id, volume, mute, solo}, ...].
  - El backend mezcla las pistas con precisión float64, aplica gain,
    gestiona solo/mute, y escribe el WAV resultante.
  - Evita clipping:
      • Calcula el pico final.
      • Si hay clipping, avisa al usuario y ofrece:
          a) Normalizar (reducir ganancia global).
          b) Aplicar un limiter suave.
          c) Exportar tal cual (con clipping).
      • No normalices silenciosamente.
      • Documenta cualquier procesamiento aplicado.
  - Exporta como mínimo WAV PCM 16-bit. Opcionalmente 24-bit, FLAC, MP3.

Exportación individual:
  - Cada pista tiene un botón "Descargar" que descarga el archivo
    individual sin procesar (tal como lo generó el modelo).
